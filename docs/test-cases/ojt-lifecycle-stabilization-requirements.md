# OJT lifecycle stabilization — Stage 1 requirements

## Boundary and evidence posture

This is a Ticket 1 documentation baseline for Stage 1 stabilization. It records the approved portfolio boundary and current, observable repository facts; it does not assert that remediation has happened. Existing behavior is characterized where the repository exposes it. A requirement is not permission to invent a status enum, report-hour rule, provider response, or happy-flow artifact.

The approved Stage 1 flow is: authenticate a seeded/synthetic student; obtain a deterministic academic profile without a default real-provider call; create a placement with its required owner and company; inspect the automatically created requirements for active categories; add descriptions and reports; submit for coordinator review; coordinator approves only when the approved review boundary is satisfied; then view an authorized filtered result and its PDF projection. The repository does not currently prove that this flow is implemented end to end.

**RED-test gate:** open questions below must be user-acknowledged and resolved before RED tests are authored or run. Ticket 1 established this specification and baseline; later tickets add the executable tests that reference these cases. Current results remain **Not Run** until those tests execute.

## Sequential requirements and acceptance boundaries

### REQ-01 — One-command Compose demonstration

Acceptance boundary: a supported macOS/Linux developer can start the Stage 1 demonstration with one documented Docker Compose command; Nginx, PHP-FPM, and MariaDB LTS become healthy and the application is reachable without undocumented manual reconstruction.

### REQ-02 — Authentication and preserved roles

Acceptance boundary: the demo accepts the existing `sr_code`/password login shape and preserves guest, student, coordinator, and superuser roles. Role-specific access is explicit, unsupported/unknown roles fail closed, and every protected API action for an authenticated unknown-role principal returns **403** safe JSON; no new status or role enum is invented.

### REQ-03 — Deterministic academic provider boundary

Acceptance boundary: registration credential verification uses only an unauthenticated, rate-limited `POST /api/academic/profile` with `sr_code` and `password` in the request body; any `sr_code` or `password` query parameter causes rejection, even when a valid POST body also contains both credentials, and this rejection occurs before any provider invocation. Credentials are never accepted through GET/query parameters. Request validation, including body-only credential and schema validation, completes before any provider invocation. The browser registration flow preserves redirect and field-level errors in HTML responses, while JSON requests use the API statuses/contracts below and validation remains **422**. One request `correlation_id` is created at the controller boundary and is identical in controller, manager, and provider logs/traces and in the response, including failures; logs/traces never contain raw request or provider payloads.

The default adapter is a deterministic fake with no network transport: approved synthetic credentials return **200** JSON containing only the normalized safe profile, placeholder photo, and enrollment fields plus `correlation_id`; provider tokens, passwords, arbitrary forbidden fields, and raw PII are never returned, logged, or persisted. Unknown credentials return **422** `{error:{code:academic_credentials_invalid,message:safe generic},correlation_id}` and may be logged only at the expected WARN/INFO level. Local fake-only deterministic timeout/unavailable scenarios return **503** with codes `academic_provider_timeout`/`academic_provider_unavailable`, and fake responses complete under one second.

Real mode is explicit environment-only opt-in via `ACADEMIC_PROVIDER_MODE`, `ACADEMIC_PROVIDER_BASE_URL`, `ACADEMIC_PROVIDER_KEY`, `ACADEMIC_PROVIDER_CONNECT_TIMEOUT_SECONDS=2`, and `ACADEMIC_PROVIDER_TIMEOUT_SECONDS=5`; a real base URL must be `https://`, except for an explicit loopback (`127.0.0.1`, `::1`, or `localhost`) sentinel allowed only when `APP_ENV` is `local` or `testing`. cURL TLS peer and host verification remain enabled. Upstream non-2xx responses map to safe **503** code `academic_provider_unavailable`. Real response normalization uses the exact fake schema and a strict whitelist: arbitrary forbidden fields/tokens/passwords/raw PII are rejected or omitted, never passed through. Malformed payloads and forbidden-field payloads return **503** with code `academic_provider_malformed`; missing configuration fails closed with **503**. Each local real-provider sentinel scenario must prove transport occurred by asserting the sentinel hit count increases by exactly one for that scenario, alongside the exact safe error code; a pre-transport configuration failure is insufficient. Unexpected failures emit a structured ERROR containing exception class, message-safe category, stack, cause, and `correlation_id` (without raw payloads); expected invalid credentials are the permitted WARN/INFO exception. Fake tests use a local sentinel/isolated endpoint to assert zero hits, and real tests may use only a local test sentinel, never the live provider. Credentials never source from, appear in, or leak through logs/responses.

### REQ-04 — Placement and evidence lifecycle

Acceptance boundary: an authorized student can create only an owned placement for an existing company, with required `company_id`, internship start/end dates where start <= end, representative, and `student_position`; owner, updater, and approval fields are server-authoritative. The create transaction creates exactly one placement-linked requirement for each active requirement category and no inactive-category requirements; placement and automatic requirements commit or roll back together. The student can manage their own placement-linked descriptions and reports through the approved lifecycle. Before approval, the student may create, read, edit, and soft-delete their own placement/evidence; approved placement, evidence, requirements, deletion actions, and visits are immutable until the explicit reopen flow. An absent description is optional, but a submitted blank/whitespace description is invalid with **422**. Authenticated `GET /api/descriptions/{id}` and `GET /api/reports/{id}` return 200 for the owner and authorized staff, 403 cross-owner, and 404 for missing/deleted resources. Description/report lists and searches remain paginated `data`/`links`/`meta` responses and exclude soft-deleted records. The authoritative lifecycle state is the conjunction of approval prerequisites and `is_approved`; `status` is display/backward-compatibility only. Approval sets `status` to `approved`, and reopen sets it to `pending`, but status alone never authorizes, completes, or reports a placement. A report requires a real date within the inclusive internship start/end dates and numeric hours from **0.25 through 24 inclusive** in **0.25-hour increments**. Existing 0/1 flags and the current backend/UI report-field mismatch remain compatibility facts.

### REQ-05 — Coordinator approval and reportable output

Acceptance boundary: a student can submit eligible evidence for coordinator review but cannot verify, validate, or approve it, and only an authorized coordinator or superuser (with superuser inheriting coordinator permissions) can verify/validate/approve when core placement fields are complete, every active requirement is verified, and at least one non-deleted valid report exists. That report must have a real date within the inclusive internship start/end dates and numeric hours from 0.25 through 24 inclusive in 0.25-hour increments. Approval is idempotent: an already-approved placement returns the current **200** representation and creates no duplicate lifecycle event. A state-changing approval or reopen atomically commits exactly one immutable lifecycle event with the state change. Reopen is `POST /api/internships/{id}/reopen`, coordinator/superuser-only, and requires a trimmed string reason of 10–500 characters; student, unknown-role, and cross-owner requests return **403**, missing placement returns **404**, and already-unapproved placement returns **409**, with no state or event change on denial/conflict. Approval sets `is_approved=true` and `status=approved`; reopen sets `is_approved=false` and `status=pending`, permits owner corrections, and prerequisites are rechecked before reapproval, which creates a new approval event. Approved placement, evidence, requirements, delete, and visit mutations remain immutable until reopen. Descriptions are optional when absent and do not gate approval; a submitted blank description is invalid. `GET /api/internships/{id}/lifecycle-events` allows the owner student and coordinator/superuser, denies cross-owner/unknown roles with **403**, returns **404** for a missing placement, and returns immutable events in stable chronological order. Each event contains only the internship numeric ID, actor numeric ID, event type, from/to approval booleans, reopen reason (null for approval), and timestamp—no PII. JSON and PDF reporting include approved placements only; pending/reopened placements are excluded and reapproved placements are included. Status never independently authorizes, completes, or reports a placement.

The filtered JSON and PDF API contracts are **POST-only**: each accepts the same shared authorized query/service and the same POST filter body; no legacy GET route, query-string filter, or other GET bypass is supported. The preserved web session form may use POST with the same default pagination values. The five required scalar filters are `campus`, `schoolyear`, `semester`, `college`, and `course`; each is a string of at most 100 characters matching only letters, numbers, spaces, hyphens, and underscores (no null, array/object, malformed, or injection-like value). Optional `page` defaults to **1** and must be an integer >= 1; optional `per_page` defaults to **15** and must be an integer from **1 through 100**. JSON and PDF honor identical `page`/`per_page` values, and exact record/value parity applies to that page only. Any invalid pagination or filter input, including injection-like input, returns safe JSON **422** with the standard error shape. Soft-deleted internships are always excluded. Role authorization uses only the resolved role contract—student own-only, coordinator/superuser authorized global set, unknown role **403**, guest **401**—with no role-compatibility fallback branch.

Both projections use stable ordering `users.first_name ASC`, `users.last_name ASC`, `internships.id ASC`. For every internship ID on the requested page, the filtered JSON and PDF have exact parity for displayed student name, synthetic SR code, company, start date, end date, approval/status, and all five academic fields; page metadata is consistent with the same `page`/`per_page` request. They contain no unauthorized records and no extra raw PII beyond the approved template. The dynamic validator is the source of truth for filter and pagination shape/range checks; it must not add a role-compatibility branch. Success returns **200 `application/pdf`**; a no-result request is a valid parseable PDF containing the filter headers and exact text `No matching records`. Repeating the same normalized input produces deterministic PDF text. When the client supplies `X-Correlation-ID`, that value is returned unchanged and appears unchanged in response, log, and trace records for both projections (including failures); a value is generated only when the header is absent. A PDF rendering failure returns safe **503** JSON (with the unchanged/logged correlation ID) and emits no partial or raw renderer output. The UI shows a clear empty state; the API/PDF and UI never leak unauthorized records.

#### REQ-05 method/status contract

| Collection surface | Expected status and response | Mutation/audit safety |
|---|---|---|
| Authenticated `GET /api/internships/{id}/lifecycle-events` | **200** read-only collection for the owner student or coordinator/superuser | Returns stable immutable events with numeric IDs/booleans/timestamp and no PII |
| Authenticated `PUT`, `PATCH`, or `DELETE` on `/api/internships/{id}/lifecycle-events` | Exact **405 Method Not Allowed** safe normalized JSON `{error:{code,message},correlation_id}` with a correlation ID | No placement state or lifecycle-event mutation; no raw exception or PII |

### REQ-06 — Authorization and ownership

Acceptance boundary: backend authorization mirrors the existing frontend RBAC for every protected placement/evidence/cluster/search read and mutation, including reopen and lifecycle-event reads. Unauthenticated API requests return **401**; authenticated-but-forbidden and cross-owner requests, including edits, soft-deletes, reopen attempts, lifecycle-event reads, and student cluster deletion, return **403**; nonexistent resources return **404** without existence disclosure; validation failures return **422** safe JSON errors; an already-unapproved reopen returns **409** without changing state or audit history. Each error response is exactly shaped as `{error:{code,message},correlation_id}` (with safe, non-sensitive values) and does not disclose record existence or PII. Student search returns **200** with own records only; coordinator and superuser may perform authorized global search; no matches return **200** with an empty data collection. A student cannot access another student’s placement or self-approve, approved records cannot be changed without the explicit coordinator reopen flow, and superuser inherits coordinator permissions. Approval authority and report inclusion are always determined by `is_approved` plus prerequisites, never by the display-only `status` value.

### REQ-07 — Safe validation, errors, and failure behavior

Acceptance boundary: malformed placement/evidence/filter inputs return **422** safe JSON errors; unauthenticated API access returns **401**; authenticated forbidden/cross-owner access returns **403**; missing resources return **404**. Errors use `{error:{code,message},correlation_id}` and never reveal record existence details or PII. Provider failures, partial failures, concurrency conflicts, empty results, loading states, and session expiry remain bounded, actionable, and non-sensitive. The server derives owner, updater, and role-sensitive fields and rejects or ignores client attempts to escalate them. Persistence does not silently create cross-owner or partial unrelated records.

### REQ-08 — Security containment and remediation boundary

Acceptance boundary: runtime secrets are environment/config-backed, synthetic fixtures contain no real PII, and the sensitive SQL dump and hard-coded provider key are contained from the distributable demo. Every application/startup/HTTP/trace/container log line and emitted diagnostic artifact is structured JSON where applicable and must redact or omit secrets, credentials, passwords, tokens, `api_key`, raw request/provider payloads, email, phone, address, and published demo credentials. The published local-only synthetic identities are `DEMO-STUDENT-001` (`demo.student.001@test.example`, password `DemoOnly-Student-001!`), `DEMO-COORD-001` (`demo.coord.001@test.example`, password `DemoOnly-Coord-001!`), and `DEMO-ADMIN-001` (`demo.admin.001@test.example`, password `DemoOnly-Admin-001!`). These credentials are non-secret demo fixtures, never production defaults, and must not contain real PII. Credential rotation and Git-history purge are documented with backup, dry-run, verification, coordination, and force-push gates; neither operation is executed in Stage 1 documentation.

### REQ-09 — Persistent, resettable, idempotent demo

Acceptance boundary: Compose-backed data persists across the supported restart path; migrations/auth initialization/seeders can be rerun without duplicate identities or broken relationships; seeded synthetic student, coordinator, and superuser fixtures are exactly the documented local-only identities `DEMO-STUDENT-001`, `DEMO-COORD-001`, and `DEMO-ADMIN-001`; an explicit local reset deterministically restores those identities and their safe synthetic fixture state without external-provider access. They are never production defaults.

Recommended supported interfaces and invariants for Stage 1 targets: automatic bootstrap on normal `docker compose up`; an explicit `docker compose exec php-fpm demo-reset` command (or equivalent named container command finalized by implementation); exactly three synthetic role identities and a deterministic fixture graph; Passport keys byte-identical across normal bootstrap/restart with a stable OAuth client count; and reset that deterministically recreates database data and OAuth clients without exposing key/client secrets or making provider network calls. If the executable name is not yet implemented, these cases specify the behavior contract while naming `demo-reset` as the preferred command.

### REQ-10 — Layered local quality gate and operational evidence

Acceptance boundary: a clean checkout runs one documented aggregate command that first validates Compose config, then runs Ticket02 `compose_contract` and Ticket03 through Ticket09 sequentially, followed by the **checked-in** Ticket10 Playwright happy-flow at `tests/E2E/ticket10_happy_flow.spec.js`; it must not depend on an external test repository or service. Until that file is checked in, the traceability CSV may use the planned `tests/Infrastructure/ticket10_acceptance_test.sh` reference only for cases that genuinely require Ticket10. The browser journey is reproducible from the repository, uses synthetic-only identities/data, and never calls a live provider. Each suite is fail-fast/max1; the aggregate continues after a forced failure, summarizes every suite and elapsed time, and exits nonzero if any suite fails or total elapsed time exceeds 600 seconds. Child timeouts are portable (`timeout` with `gtimeout` fallback), and the complete gate is run twice (failure-injection and all-pass) with the same ordering.

All logs, traces, screenshots, videos, reports, and other evidence are generated in a deterministic system temporary directory outside the repository. The JSONL manifest is also outside the repository and has one object per artifact with `case`, `artifact`, `sha256`, `source`, `contains_secrets`, `revision`, `command`, and `timestamp`; `sha256` is the SHA-256 digest of the artifact bytes, `source` identifies the producing suite/command, and `contains_secrets` must be false. The validator rejects missing IDs, unsupported types, blank/nonexistent refs, missing requirements, repository containment, hidden/untracked output, malformed manifest records, and any secret-bearing artifact. It validates the CSV's 43 sequential cases and 10/10 requirement coverage from a clean checkout rather than trusting hard-coded counts.

The gate covers the browser happy flow, HTTP/API contracts, domain/service invariants, operational health/reset/idempotence, security regression, startup/bootstrap failure observability, structured JSON correlation-safe logging, secret-safe traces/container output/artifacts, and the requirements/test/baseline evidence package. Every nonempty application/startup log line is JSON with `timestamp`, `level`, `event`, `component` or `operation`, and `status`; HTTP events carry the request `correlation_id`; unexpected ERROR events carry `exception_class`, `error_category`, safe `message_category`, `stack`, and `cause`; invalid credentials are WARN/INFO only. No secret, credential, password, token, `api_key`, raw payload, email, phone, address, or demo credential may appear in logs, traces, or artifacts. Supported forced-failure injection names one early suite, proves aggregate continuation and nonzero summary, and is followed by a clean repeat pass. Ticket08 remains the DB-level lifecycle mutation-rejection contract; Ticket10 verifies the API-visible immutable event projection without direct database writes.

Future happy-flow documentation is **unsealed** until Compose startup/reset, the authoritative browser journey, linked API/domain/security/regression tests, the aggregate gate, artifact-manifest validation, and the repeat pass all succeed **and an explicit approval record is present**. The approval record must identify the approver, scope, clean-checkout revision, command, timestamp, and evidence manifest. Credential rotation and Git-history rewrite/purge remain documentation-only and execution-approval-gated; no rotation, history rewrite, force-push, or purge is performed by this gate.
