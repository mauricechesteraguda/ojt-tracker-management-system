## Approved flow boundary

The resolved academic-profile boundary is an unauthenticated, rate-limited `POST /api/academic/profile` carrying only body fields `sr_code` and `password`; GET/query credentials are prohibited and must be rejected without a provider call. Validation completes before provider invocation. One request `correlation_id` must propagate unchanged through controller/manager/provider logs and traces and the response, including failures; raw request/provider payloads are never logged or returned. The default fake adapter has no network transport: known synthetic credentials return 200 JSON with only the normalized safe profile/photo/enrollment schema; unknown credentials return 422 `academic_credentials_invalid`; fake-only timeout/unavailable cases return 503 `academic_provider_timeout`/`academic_provider_unavailable` and complete under one second. Fake tests assert zero hits against a local sentinel/isolated endpoint.

Real mode is explicit environment-only opt-in using `ACADEMIC_PROVIDER_MODE`, `ACADEMIC_PROVIDER_BASE_URL`, `ACADEMIC_PROVIDER_KEY`, `ACADEMIC_PROVIDER_CONNECT_TIMEOUT_SECONDS=2`, and `ACADEMIC_PROVIDER_TIMEOUT_SECONDS=5`. A real base URL is HTTPS, with only an explicit loopback sentinel exception under `APP_ENV=local` or `APP_ENV=testing`; cURL TLS peer/host verification is enabled. Upstream non-2xx maps to safe 503. Real normalization is the same strict whitelist/schema as fake normalization and rejects or omits arbitrary forbidden fields, tokens, passwords, and raw PII. Missing configuration fails closed 503; malformed payloads return 503 `academic_provider_malformed`; correlation-safe structured ERROR logging includes exception class, message-safe category, stack, cause, and correlation_id for unexpected failures, while expected invalid credentials may be WARN/INFO. Credentials, secrets, and payloads never appear in responses or logs. The live provider is never used by tests.

The Stage 1 target flow is authentication → deterministic fake academic profile → placement with owner/company → generated requirements → description/report evidence → submission → coordinator review/approval → authorized filtered view → PDF projection. The default provider makes no network call; known synthetic SR credentials return normalized profile, placeholder photo, and enrollment metadata; unknown credentials return safe 422 JSON; explicit timeout/unavailable scenarios return safe 503; real-provider access is opt-in with environment-held credentials and no secret/PII logging. Approval requires complete core placement fields, every active requirement verified, and at least one non-deleted valid report; that report has a real date within inclusive internship start/end dates and numeric hours from 0.25 through 24 in 0.25 increments; descriptions are optional. Before approval, students may edit/soft-delete their own descriptions/reports; approved records are immutable. An authorized coordinator may explicitly reopen a placement only with a required audit reason, returning it to unapproved state for student corrections. Successful approval drives completion through `is_approved`; free-string `status` is display/backward-compatibility only and must not drive authorization or completion. Filtered JSON and PDF APIs are POST-only with no legacy GET bypass and use one shared authorized POST-body query/service; the preserved session web form may POST with defaults `page=1` and `per_page=15`. Required scalar filters are `campus`, `schoolyear`, `semester`, `college`, and `course`; each is <=100 characters and limited to letters, numbers, spaces, hyphens, and underscores. Optional page is integer >=1, default 1; per_page is integer 1–100, default 15; invalid pagination returns 422. JSON and PDF use identical page/per_page and exact parity applies to that page. Soft-deleted internships are always excluded; student filtered views are own-only, coordinator/superuser views are global, unknown roles are 403, and guests are 401 with no role-compatibility branch. Both outputs order by `users.first_name ASC`, `users.last_name ASC`, `internships.id ASC` and have exact per-internship-ID parity for displayed student name, synthetic SR code, company, start/end, approval/status, and all five academic fields, with no unauthorized records or extra raw PII. A supplied `X-Correlation-ID` is unchanged in response/log/trace for both outputs, including failures. Successful PDF responses are 200 `application/pdf`; no-result PDFs are parseable, include filter headers and exact `No matching records`; normalized repeats have deterministic text; rendering failures return safe 503 JSON and emit no partial/raw output. No-result UI shows a clear empty state. Student search returns 200 own-only with no cross-owner names/IDs; coordinator and superuser have authorized global search, and no matches return 200 with an empty data collection. Authorized coordinator/superuser cluster deletion returns 204, detaches linked internships (`cluster_id=null`), and soft-deletes the cluster; student and unknown-role deletion returns 403 and missing clusters return 404. This is a target acceptance boundary, not a claim that the current application completes it. The resolved authorization contract is: backend mirrors existing frontend RBAC; unauthenticated API is 401; authenticated forbidden, cross-owner, and unknown-role access are 403; nonexistent resources are 404; validation failures are 422 safe JSON `{error:{code,message},correlation_id}` without existence details or PII. The server derives owner/updater/role-sensitive fields and rejects or ignores client escalation. Superuser inherits coordinator permissions; student creation is own-only and student self-approval remains prohibited.

Published local-only synthetic fixtures (non-secret; never production defaults): `DEMO-STUDENT-001` / `demo.student.001@test.example` / `DemoOnly-Student-001!`; `DEMO-COORD-001` / `demo.coord.001@test.example` / `DemoOnly-Coord-001!`; `DEMO-ADMIN-001` / `demo.admin.001@test.example` / `DemoOnly-Admin-001!`. These identities use no real PII, and deterministic reset restores them and their safe synthetic data.

The lifecycle target additionally fixes the state/audit contract: approval prerequisites plus `is_approved` are authoritative; `status` is display-only, set to `approved` on approval and `pending` on reopen, and never independently authorizes, completes, or reports. `POST /api/internships/{id}/reopen` is coordinator/superuser-only and requires a trimmed 10–500 character reason; student/unknown/cross-owner is 403, missing is 404, and already-unapproved is 409, with no denied/conflicting state or event change. `GET /api/internships/{id}/lifecycle-events` is allowed to the owner student and coordinator/superuser, returns stable chronological immutable approve/reopen events containing only numeric internship/actor IDs, event type, from/to approval booleans, reason (null for approve), and timestamp, with no PII. Approval is idempotent (current 200, no duplicate event); actual approval/reopen each create one event transactionally. JSON/PDF reporting is approved-only: pending/reopened are excluded and reapproved is included.

## Risks

1. Legacy Laravel/PHP/Passport versions may constrain a reproducible runtime.
2. Empty seeding and absent Docker evidence prevent a deterministic clean-run baseline.
3. `ojt.sql` and the hard-coded provider key create exposure and fixture-contamination risk.
4. Current backend authorization gaps may violate the resolved frontend-RBAC and 401/403/404/422 response contract.
5. Free-string internship status could be incorrectly used as a lifecycle/authorization source; the resolved contract makes approval prerequisites and `is_approved` authoritative, with status display-only, descriptions optional, and blank submitted descriptions invalid.
6. UI/backend report-field mismatch can produce ambiguous validation and no safe hour-rule assertion.
7. The resolved UI/PDF filter parity, stable ordering, exact-record/value, no-result, and no-leakage contract must be implemented consistently; real-provider success beyond explicit opt-in is not part of the default demo.
